はい、**Phase 6 が一通り終わってからで良い**と思います。
むしろ今 Cosmos DB を差し込むと、せっかく安定してきた Phase 6 の確認軸が増えて、デモ直前の事故率が上がります。

おすすめはこうです。

```text id="9l8j83"
今すぐやる:
Phase 6.1〜6.5 の本番確認
- ログイン
- サイト分離
- 検索
- 神田フレーム投入
- グッジョくん生成UI
- 事故報生成〜確認〜確定
- 施設ナレッジ改善

その後にやる:
Phase 6.6 Cosmos DB エージェントイベントログ
```

Cosmos DB は **主機能を壊さずに後付けできる場所**に入れるのが良いです。
つまり、SQL の正本データや既存フローを置き換えず、

```text id="g520rj"
Worker が各ステップで appendAgentEvent する
失敗しても本線処理は止めない
UI は events が取れたら表示、なければ既存の疑似ステップ表示
```

くらいの “横に足す” 実装にする。

実装判断としては、まず Phase 6 のデモが通ったあとで、

```text id="vbeejh"
余力あり:
  Cosmos DB で実行ログ保存 + /api/reports/[id]/events

余力なし:
  デモ説明では「次に Cosmos DB にエージェントイベントログを蓄積する設計」として話す
```

で十分です。

特に今は、Cosmos DB より先にこの確認が大事です。

```text id="wvj1c6"
kanda / goodjob でログイン
↓
神田事務所サイトとして事故報作成
↓
動画抽出フレームが候補に出る
↓
グッジョくんUIで生成中演出
↓
waiting_human_review
↓
人間修正
↓
confirm
```

ここが通れば、もうデモの核はかなり強いです。

なので結論は、**Phase 6 完了後に Phase 6.6 として Cosmos DB を足す**。
実装する場合も、既存処理の依存先にはせず、ログ用途の optional integration にするのが安全です。
```
